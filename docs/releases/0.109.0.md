# DolphinClient 0.109.0 — Real sessions, and email addresses that are actually verified

Target: `deploy/account-api.mjs` and the website's `/dashboard`. This release
does not touch the client or launcher.

## Changes

- **Email verification.** Registration now sends a real confirmation link
  when the server has SMTP configured (`ACCOUNT_SMTP_HOST` etc., the same
  variables password-reset mail already used), instead of trusting whatever
  address was typed. The link points at a new `/verify` page, valid for 24
  hours, and confirming it sets a new `users.email_verified_at` column. The
  dashboard's Account card shows a plain "Not verified" status with a
  one-click resend (`POST /auth/resend-verification`, rate-limited like every
  other auth route) when it isn't set.
  - A server with **no mail configured** marks every new account verified at
    registration — there's no way to prove an address without a mail server,
    so the feature disables itself the same way password-reset mail already
    does, rather than leaving accounts stuck "unverified" forever with no
    way to fix it.
  - An **existing deployment's database** migrates in place: the column is
    added if missing, and every row that predates the feature is backfilled
    to already-verified (using its own `created_at`) the moment the service
    starts — no manual migration step, and no existing user is suddenly
    locked out of anything by an upgrade.
- **Real session management.** The dashboard's Sessions card used to offer
  exactly two buttons ("sign out" and "sign out everywhere") with no way to
  see what "everywhere" actually meant. `GET /sessions` now lists every
  active session for the signed-in account — a rough browser/OS label parsed
  from its user agent, its IP, when it was created, and which one is the
  current request — and the dashboard renders that list with a per-session
  "revoke" (`DELETE /sessions/:id`) next to the existing "sign out
  everywhere". A session's id is its existing token digest — an HMAC over
  the real session token, already stored as the sessions table's primary
  key — so exposing it to the client identifies the row without handing out
  anything that could be replayed as that session (the digest can't be
  inverted back to a token that reproduces it).
- **Tests.** `deploy/test-account-api.mjs` gained coverage for the new
  routes: registration auto-verifying with no mail server, `/auth/verify`
  rejecting a bad token, `/auth/resend-verification` being a no-op once
  verified, `/sessions` listing and correctly marking the current one, and
  revoking a *different* session (via a second independent login) actually
  invalidating it — plus the usual "refused without a session" checks for
  every new authenticated route.

## Reference

No new environment variables: verification mail reuses the existing
`ACCOUNT_SMTP_*` configuration described in `account-api.mjs`'s header
comment and `deploy/README.md`. No deployment script changes were needed —
`setup-account-api.sh` already installs and restarts the one service both
features live in.
