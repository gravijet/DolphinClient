## 1. BlockState: internal representation & vanilla id identity

`azalea_block::block_state::BlockState` (re-exported as `azalea_block::BlockState`):

```rust
pub type BlockStateIntegerRepr = u16;           // azalea_block::block_state::BlockStateIntegerRepr

#[derive(Clone, Copy, Default, Eq, Hash, PartialEq)]
pub struct BlockState { id: BlockStateIntegerRepr }   // field is PRIVATE

impl BlockState {
    pub const AIR: BlockState;                                   // id 0
    pub const MAX_STATE: BlockStateIntegerRepr;                  // = 29872 for mc26.1 (generated)
    pub const fn id(&self) -> BlockStateIntegerRepr;             // "protocol ID"
    pub const fn is_valid_state(state_id: BlockStateIntegerRepr) -> bool;
    pub fn is_air(&self) -> bool;
    pub fn property<P: Property>(self) -> Option<P::Value>;      // generated
    pub fn as_block_kind(self) -> BlockKind;                     // generated, O(1) table lookup
}
// TryFrom<u32>, TryFrom<i32>, TryFrom<u16> (Error = ()), From<BlockState> for u32,
// From<BlockKind> for BlockState (default state), From<BlockState> for BlockKind
```

The internal repr is **`u16`** in this release (`BlockStateIntegerRepr` type alias; the doc comment says it can be u16 or u32, and `From<BlockState> for u32` exists so treating it as u32 is safe).

**Is the id identical to vanilla's global block-state id?** Yes.
Evidence:
- `impl AzBuf for BlockState` (block_state.rs:122) reads the id as a **raw protocol varint with no remapping** — this is the type used directly in `ClientboundBlockUpdate { pub block_state: BlockState }` and chunk-section palettes (`azalea_world::palette::PalettedContainer<BlockState>`). If the ids differed from the vanilla global palette, azalea could not parse worlds at all.
- ids are assigned by `azalea-block-macros::make_block_states!` sequentially in block-declaration order, last property varying fastest, mirroring vanilla's state enumeration; `generated.rs` header: "This code is @generated by codegen/genblocks.py" (codegen runs against the matching vanilla version).
- Empirical values from the compiled probe match the vanilla `blocks.json` report layout:
  `air`=0, `stone`=1, `grass_block`=8..=9 (default 9, i.e. `snowy=true`→8, `snowy=false`→9),
  `water`=86..=101, `lava`=102..=117, `oak_stairs`=3907..=3986 (default 3918), `MAX_STATE`=29872.
- Quirk: for **bool** properties `true` sorts before `false` (macro comment "it starts with true for some reason") — same as vanilla.

`Debug` prints `BlockState(id: 3918, OakStairs { facing: North, ... })`.

## 2. BlockState → block name string ("minecraft:oak_stairs")

Two routes; both `&'static str` / zero-alloc-capable:

```rust
use azalea_block::{BlockState, BlockTrait};
use azalea_registry::builtin::BlockKind; // NOTE: `azalea_registry::Block` is a DEPRECATED alias of this

fn names(state: BlockState) {
    // route A: via the registry enum — namespaced
    let kind: BlockKind = state.as_block_kind();
    let full: &'static str = kind.to_str();         // "minecraft:oak_stairs"
    let disp = format!("{kind}");                   // Display = to_str()

    // route B: via the block struct — path only, no namespace
    let block: Box<dyn BlockTrait> = Box::from(state);
    let path: &'static str = block.id();            // "oak_stairs"
    println!("{full} {disp} {path}");
}
```

`BlockKind` is `#[repr(u32)]`, implements `azalea_registry::Registry { fn from_u32(u32) -> Option<Self>; fn to_u32(&self) -> u32 }`, `FromStr` (accepts `"oak_stairs"` or `"minecraft:oak_stairs"`), `Display`, `TryFrom<u32>`, `From<BlockKind> for Identifier`. 1168 variants in mc26.1 (block registry ids 0..=1167). `Identifier` (renamed from `ResourceLocation` in 0.16) has `new(impl Into<String>)`, `namespace() -> &str`, `path() -> &str`.

## 3. GENERIC property access — YES, fully string-based (build variant keys without blocks.json)

`azalea_block::BlockTrait` (object-safe, `Box<dyn BlockTrait>: From<BlockState>`):

```rust
pub trait BlockTrait: Debug + Any {
    fn behavior(&self) -> BlockBehavior;
    fn id(&self) -> &'static str;
    fn as_block_state(&self) -> BlockState;
    fn as_block_kind(&self) -> BlockKind;
    fn property_map(&self) -> HashMap<&'static str, &'static str>;          // ALL props as strings
    fn get_property(&self, name: &str) -> Option<&'static str>;
    fn set_property(&mut self, name: &str, new_value: &str) -> Result<(), InvalidPropertyError>; // new in 0.16
}
impl dyn BlockTrait { pub fn downcast_ref<T: BlockTrait>(&self) -> Option<&T>; }
```

Values are exact vanilla strings: bools `"true"`/`"false"`, ints `"0"`,`"1"`,…, enums `"north"`, `"inner_left"`, `"bottom"`, etc. This is sufficient to build blockstate-JSON variant keys directly — **the blocks.json report dependency can be dropped**. Verified compiled example:

```rust
use azalea_block::{BlockState, BlockTrait};

/// e.g. state 3919 -> ("minecraft:oak_stairs", "facing=north,half=bottom,shape=inner_left,waterlogged=true")
fn variant_key(state: BlockState) -> (String, String) {
    let block: Box<dyn BlockTrait> = Box::from(state);
    let name = state.as_block_kind().to_str().to_string();
    let mut props: Vec<(&str, &str)> = block.property_map().into_iter().collect();
    props.sort(); // property_map is a HashMap (unordered); vanilla blockstate-JSON keys are alphabetical
    let key = props.iter().map(|(k, v)| format!("{k}={v}")).collect::<Vec<_>>().join(",");
    (name, key)
}
```

Mutation also works generically: `let mut b = Box::<dyn BlockTrait>::from(state); b.set_property("facing", "east")?; let new_state = b.as_block_state();` (verified: oak_stairs default 3918 → facing=east,waterlogged=true → 3977).

Typed access still exists: concrete structs in `azalea_block::blocks` (e.g. `blocks::OakStairs { facing: properties::FacingCardinal, half: properties::TopBottom, shape: properties::StairsShape, waterlogged: bool }`), property enums in `azalea_block::properties`. `pub trait Property: FromStr { type Value; fn try_from_block_state(BlockState) -> Option<Self::Value>; fn to_static_str(&self) -> &'static str; }` — for bool-like properties `Value = bool`, for enums `Value = Self`. Property enums also impl `Display`, `From<BlockStateIntegerRepr>`.

Caveats:
- Duplicate property names on one block get suffixed **field** names (`has_bottle_0`…), but `property_map()` keys use the suffixed names too in that case (name collision handling in macro, lib.rs of azalea-block-macros lines 183-221). Affects brewing stands (`has_bottle_0/1/2`) etc. — vanilla calls these `has_bottle_0`… as well, so keys still match vanilla.
- Property struct names are azalea-specific (`FacingCardinal`, `TopBottom`, `WaterLevel`); the *string* names/values are vanilla's.

- `BlockState::MAX_STATE == 29872` for mc26.1 (measured). Total valid states = **29873** (ids `0..=29872`, contiguous, no gaps).

## 5. Waterlogged & FluidState

Generic waterlogged check (both verified):

```rust
use azalea_block::{BlockState, properties};

fn is_waterlogged(state: BlockState) -> bool {
    state.property::<properties::Waterlogged>().unwrap_or_default() // Option<bool>, None if no such prop
}
// or string-generic: Box::<dyn BlockTrait>::from(state).get_property("waterlogged") == Some("true")
```

`azalea_block::fluid_state` (NOT re-exported at crate root — use full path):

```rust
pub struct FluidState { pub kind: FluidKind, pub amount: u8, pub falling: bool }
pub enum FluidKind { #[default] Empty, Water, Lava }
impl FluidState {
    pub fn new_source_block(kind: FluidKind, falling: bool) -> Self;
    pub fn height(&self) -> f32;      // amount / 9.0  (0..1 fraction of a block)
    pub fn is_empty(&self) -> bool;   // amount == 0
    pub fn affects_flow(&self, other: &FluidState) -> bool;
    pub fn is_same_kind(&self, other: &FluidState) -> bool;
}
pub fn to_or_from_legacy_fluid_level(level: u8) -> u8;   // 8 - level (saturating)
// From<BlockState> for FluidState, From<FluidState> for BlockState
```

Semantics of `From<BlockState>` (fluid_state.rs): any state with `waterlogged=true` → `Water, amount 8`; `BlockKind::Water`/`Lava` → amount = `8 - level` (`level` block property 0 = source; `level >= 8` = falling in vanilla, here it just saturates to amount 0); `BubbleColumn` → water source (amount 8). **`amount` range is 0..=8 here** (9 = "full with same fluid above" is documented but never produced), and **`falling` is always `false` — explicit TODO in source**. So azalea gives you fluid level/height per block, but for vanilla-accurate surface heights you must yourself: (a) treat `level >= 8` block property as falling/full, (b) do the corner-height averaging across neighbors — azalea has no flow-direction/corner API.
Fluid registry enum also exists: `azalea_registry::builtin::Fluid { Empty, FlowingWater, Water, FlowingLava, Lava }`.

## 6. Biomes & Items

**Biome** is a *data-driven* registry (server defines it at login), NOT a static enum:
- `azalea_registry::data::Biome` = opaque `struct { id: u32 }` implementing `DataRegistry { const NAME = "worldgen/biome"; fn protocol_id(&self) -> u32; fn new_raw(u32) -> Self }` plus `Default`/`From<u32>`/`Into<u32>` (needed for palettes). This u32 is the id used in chunk biome palettes: `azalea_world::Section { pub states: PalettedContainer<BlockState>, pub biomes: PalettedContainer<Biome> }`; `Instance`→**`World`** (0.16 rename) has `fn get_biome(&self, pos: BlockPos) -> Option<Biome>` (biomes are per 4×4×4 cell; `ChunkBiomePos: From<BlockPos>` handles the /4).
- Vanilla biome *names* enum: `azalea_registry::data::BiomeKey` (65 variants `Badlands..WoodedBadlands` + `Other(Identifier)`; has `BiomeKey::ALL`).
- Name resolution & data: via `azalea_core::registry_holder::RegistryHolder` (stored per-world; also `azalea::Client::with_resolved_registry(...)` / `resolve_registry_key(...)` helpers in `azalea/src/client_impl/mod.rs`). `Biome` implements `azalea_core::data_registry::ResolvableDataRegistry` with `DeserializesTo = simdnbt::owned::NbtCompound` (raw NBT — azalea has **no typed biome accessor wired up**):

```rust
use azalea_core::{data_registry::ResolvableDataRegistry, registry_holder::RegistryHolder};
use azalea_registry::data::Biome;

fn biome_colors(biome: Biome, registries: &RegistryHolder) -> Option<(u32, Option<i32>, Option<i32>)> {
    let (name, nbt) = biome.resolve(registries)?; // (&Identifier, &NbtCompound)
    let effects = nbt.compound("effects")?;
    let water_color = effects.int("water_color")? as u32;   // always sent by vanilla
    let grass_color = effects.int("grass_color");            // Option — only some biomes (e.g. swamp)
    let foliage_color = effects.int("foliage_color");        // Option
    let _ = name;
    Some((water_color, grass_color, foliage_color))
}
```

- The NBT the server sends per biome (vanilla): `has_precipitation`, `temperature`, `downfall`, `temperature_modifier?`, `effects: { sky_color, fog_color, water_color, water_fog_color, foliage_color?, grass_color?, grass_color_modifier?, music?, mood_sound, ... }`. azalea-core even has matching typed structs `azalea_core::registry_holder::dimension_type::{WorldTypeElement, BiomeEffects, BiomePrecipitation}` (BiomeEffects fields: `sky_color: u32, fog_color: u32, water_color: u32, water_fog_color: u32, foliage_color: Option<u32>, grass_color: Option<u32>, grass_color_modifier: Option<String>, ...`) — they derive `simdnbt::Deserialize`, so you can deserialize the biome compound into `WorldTypeElement` yourself; they're just not registered in `RegistryHolder` (only `dimension_type` and `enchantment` are typed; everything else lives in `RegistryHolder.extra: HashMap<Identifier, RegistryType<NbtCompound>>`).
- **Default grass/foliage colors are NOT in azalea anywhere**: when `grass_color`/`foliage_color` are absent, vanilla computes them from `temperature`+`downfall` sampled into `assets/minecraft/textures/colormap/grass.png`/`foliage.png` — the renderer must ship/load those colormaps from the client jar/resource pack. Same for `grass_color_modifier` (`"swamp"`/`"dark_forest"`).

**Items** (hotbar icons): `azalea_registry::builtin::ItemKind` — static enum, same generated API as BlockKind (`to_str() -> &'static str` e.g. `"minecraft:diamond_sword"`, `to_u32()`, `from_u32()`, `FromStr`, `Display`). Verified: `ItemKind::DiamondSword.to_u32() == 937`, `"minecraft:oak_stairs".parse::<ItemKind>()` works (id 442). Inventory slots: `azalea_inventory::ItemStack` has `pub fn kind(&self) -> ItemKind`; `azalea_inventory::ItemStackData { pub count: i32, pub kind: ItemKind, pub components: ... }`. Icon lookup = `item.to_str()` path → `assets/minecraft/textures/item/<path>.png` / item model JSON.

## 7. Block hardness/physics data — BlockBehavior (no opacity!)

`azalea_block::BlockBehavior` (behavior.rs), obtained per state via `Box::<dyn BlockTrait>::from(state).behavior()` (values are per *block*, not per state):

```rust
pub struct BlockBehavior {
    pub friction: f32,                       // default 0.6 (ice 0.98, slime 0.8, ...)
    pub jump_factor: f32,                    // default 1.0 (honey 0.5)
    pub destroy_time: f32,                   // vanilla "hardness"; default 0.0; -1.0 = unbreakable
    pub explosion_resistance: f32,
    pub requires_correct_tool_for_drops: bool,
    pub force_solid: Option<bool>,
}
```

- **No opacity / light-block / light-emission / propagates-skylight data exists in azalea-block** (grepped whole crate + azalea-world + azalea-physics: nothing). azalea-world also stores **no light sections** (chunk `Section` = states + biomes only; the light arrays from `ClientboundLevelChunkWithLight` are not kept). A renderer needs its own opacity/luminance table (from client jar assets or a one-time data dump) and its own light engine, or approximate opacity via collision shapes:
- Collision/outline shapes ARE available: `azalea_physics::collision::BlockWithShape` — `fn collision_shape(&self) -> &'static VoxelShape`, `fn outline_shape(&self) -> &'static VoxelShape`, implemented for `BlockState` (generated per state id). Useful for block outlines/targeting; full-cube checks can approximate "solid opaque".
- Block tags: `azalea_registry::tags::blocks` exposes `pub static LEAVES/LOGS/...: LazyLock<RegistryTag<BlockKind>>` (`RegistryTag<R>` derefs to `[R]`, has `contains(&R)` via binary search); also `tags::{items, fluids, entities}`. Handy for renderer special-cases (leaves cutout, etc.).

## Open questions

- **Exact-id cross-check vs the official 26.1 blocks.json report was done by spot-check only** (air/stone/grass_block/water/lava/oak_stairs ids + MAX_STATE all consistent with vanilla layout, and the protocol round-trips). Recommend a one-time CI assert: iterate `variant_key()` over all 29873 states and diff against the data-generator report before fully deleting it.
- `FluidState.falling` is always `false` (azalea TODO); water/lava `level >= 8` (block property) must be interpreted by the renderer itself for falling-fluid columns; no corner-height/flow-direction API — implement vanilla's `getHeight`/`getFlow` math client-side.
- Whether vanilla mc26.1 servers still send full biome `effects` NBT unconditionally (they did through 1.21.x; azalea deserializes whatever arrives into `RegistryHolder.extra["minecraft:worldgen/biome"]`). Verify against a real 26.1 server once the wire is up.
- `property_map()` allocates a fresh `HashMap` per call and `Box::<dyn BlockTrait>::from(state)` allocates; for the mesher, build a `Vec<(name, key)>` lookup table indexed by state id once at startup (29873 entries) instead of calling per block.
- `grass_color_modifier` handling ("swamp", "dark_forest") and the temperature/downfall→colormap sampling are entirely renderer-side; azalea provides only the raw NBT fields.
