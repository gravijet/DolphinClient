# DolphinClient 0.112.0 — Profiles, two-factor authentication, and login history

Target: `account-api.mjs`, and three new/changed website pages: `/dashboard/profile`,
`/dashboard/security`, and `/login`. This release does not touch the client or launcher.

## Changes

### Public profiles

- Accounts can now set a bio (up to 500 characters), an avatar URL, and social handles for
  Twitter/X, Discord, GitHub and YouTube.
- New `/dashboard/profile` page: a live avatar preview, a bio textarea with a character counter, and
  one input per social platform. Discord's old `name#1234` discriminator format is accepted.
- Backend: `PATCH /profile` accepts `bio`, `avatar_url`, `social_links` alongside the existing
  `display_name`/`minecraft_username`. `avatar_url` must be a valid `http(s)://` URL (it's rendered
  as an `<img src>`); social handles are limited to `[A-Za-z0-9._#-]`.

### Two-factor authentication (TOTP)

- New `/dashboard/security` page walks through setup: generates a secret, renders a scannable QR
  code client-side (via the `qrcode` npm package — the secret is never sent to a third party to
  render), and a manual-entry fallback for the raw secret. Confirming with a real 6-digit code from
  an authenticator app enables 2FA and hands back 10 one-time backup codes (copy or download as
  `.txt`), shown exactly once.
- Login becomes two-step for an account with 2FA on: `POST /auth/login` returns
  `{requires_totp: true, challenge}` instead of a session after the password checks out; the
  frontend then asks for a code and calls `POST /auth/login/totp` with the challenge. A backup code
  works in place of the 6-digit code and is invalidated after one use.
- Disabling 2FA (`POST /totp/disable`) and regenerating backup codes
  (`POST /totp/regenerate-backup-codes`) both require the account password, so a hijacked session
  cookie alone can't turn 2FA off or mint new backup codes.
- The TOTP implementation (RFC 6238 over HMAC-SHA1, 6 digits, 30-second steps, ±1 step of clock
  drift tolerance) is hand-rolled with Node's built-in `crypto` module — no new runtime dependency.
  It was checked against the RFC 4226 reference test vectors during development. Backup codes are
  hashed with the same HMAC digest sessions already use; only the hash is ever stored.

### Login history

- Every sign-in attempt — success or failure, including registrations, wrong passwords, banned
  accounts, and failed 2FA codes — is now logged with its timestamp, IP, user agent, and result.
- Best-effort geolocation (city/country via a free IP-lookup service, capped at a 2-second timeout,
  skipped entirely for private/loopback IPs) is filled in asynchronously after the response, so it
  never adds latency to — or can ever fail — a login.
- `GET /login-history` returns the last 50 attempts for the signed-in account, shown as a table on
  `/dashboard/security`.

## Reference

### Database migration

Six new columns on `users` (`bio`, `avatar_url`, `social_links`, `totp_secret`, `totp_enabled_at`,
`totp_backup_codes`) and three new tables (`login_history`, `totp_pending`, `totp_challenges`) are
created automatically on the next `account-api.mjs` startup — no manual migration step. Every
existing account is unaffected until it opts into the new profile fields or 2FA.

### New dependency

`qrcode` (plus `@types/qrcode` for the build) was added to the `website` workspace — it renders the
setup QR code entirely client-side from the `otpauth://` URL the backend returns; no network call,
no secret ever leaves the browser except to `account-api.mjs` itself for verification.

### Deployment

No changes to deployment scripts, systemd units, or environment variables. The existing
`dolphinclient-account-api.service` picks up every new endpoint on its next restart.
